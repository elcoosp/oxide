# Local development

Oxide builds with **Rust 1.98** (pinned in `rust-toolchain.toml`) and **Node 24+**.
The package manager is pinned to an exact version, and the pin is enforced.

## The pnpm pin

`package.json` carries:

```json
"packageManager": "pnpm@12.16.1"
```

Corepack reads this. `corepack enable` installs a shim, and the shim refuses to
run any other pnpm. That is deliberate — a lockfile generated by pnpm 10 and a
store written by pnpm 12 produce different `node_modules` layouts, and the
failure surfaces much later as `MODULE_NOT_FOUND` on a `.bin` shim.

```bash
corepack enable
corepack prepare pnpm@12.16.1 --activate
pnpm --version   # 12.16.1
```

CI pins the same version in every `pnpm/action-setup` step, as a workflow
input rather than only as the `packageManager` field, so a mismatch fails at
the setup step instead of three jobs later.

## Where pnpm settings live

**pnpm 11 moved every project setting out of `.npmrc`.** Only auth and registry
keys are still read there; everything else is silently ignored. This bit us
once — a `node-linker=hoisted` in `.npmrc` stopped taking effect the day the
toolchain crossed 11, and the failure was a build error about a missing file,
not a configuration warning.

All project settings live in `pnpm-workspace.yaml`:

```yaml
allowBuilds:
  esbuild: false
strictDepBuilds: false
strictPeerDependencies: false
autoInstallPeers: true
pmOnFail: error
```

`allowBuilds: { esbuild: false }` is a **reviewed denial**, not an oversight.
`esbuild` resolves its platform binary through `optionalDependencies`
(`@esbuild/<platform>-<arch>`), so its postinstall is redundant. Denying it
keeps `pnpm install --frozen-lockfile` green without running arbitrary install
scripts. If a dependency genuinely needs a postinstall, add it here with
`true` — do not remove `strictDepBuilds`.

## No `nodeLinker`

There is deliberately no `nodeLinker` key. Under pnpm 12's hoisted linker,
peer-qualified `.pnpm` entries are created as stubs without the package
contents. The symptom is specific: `tsdown`'s `.bin` shim points at
`…/tsdown/dist/run.mjs` inside a directory that exists but has no `dist/`. The
default (isolated) linker uses a canonical entry and works. Do not reintroduce
hoisted without a reproduction that isolated cannot satisfy.

## The commands

```bash
corepack pnpm install --frozen-lockfile
cargo build --workspace --all-targets

# the website is excluded from CI because it consumes the framework
pnpm --filter oxide-website run dev
pnpm --filter oxide-website run build
pnpm --filter oxide-website run typecheck
```

## If your shell exports `RUSTC_WRAPPER`

A build cache like `kache` works by wrapping `rustc`. If it is on your
interactive `PATH` but not on a script's `PATH`, `cargo publish --dry-run` will
fail at the verification step with `could not execute process <wrapper> (never
executed)`, which reads like a broken toolchain. Either make sure the wrapper
is on `PATH` for whatever shell runs the command, or unset it for that
invocation. CI never sets it.
