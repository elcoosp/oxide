# Benchmark report (§21)

Generated by `benchmarks/run.sh` on **2026-10-21** at HEAD `88a8787`.
Every number is a **wall-clock measurement of this machine** (Apple Silicon
macOS, debug `oxide-cli`, warm OS caches), not a spec target. §21's targets
compare against an incumbent (Next / Nuxt / SvelteKit / SolidStart) on
identical hardware; no incumbent is installed here, so the table records the
raw numbers and marks the incumbents as a TODO.

**Two changes since the 2026-10-19 report** (HEAD `b55f388`):

1. **ComponentSource migration** (`76bc400..bfff3c6`): route components
   resolve from `dist/server/ssr/index.js` (prod) or the dev source map,
   not from a `componentFor` closure in `oxide.config.ts`. That migration
   also fixed two bugs the old report could not see: every real-SSR page
   was 500ing `no component resolved` once the closure was gone, and the
   bundler was inlining React/Vue/Svelte/Solid into the SSR bundle (two
   Reacts → "invalid hook call"). Both closed.
2. **Lazy entry + renderer warm-up** (`90d0a1a`, this run): the bundler
   emits `ssr/lazy.js` alongside `ssr/index.js`; the render path uses the
   lazy one and only imports the matched route. A `warm()` hook on
   `PageRenderer` renders a synthetic route at boot so the worker pool
   and config are primed before `/_oxide/ready` returns 200.

The **liveness / readiness split** is the key design move:

| endpoint             | meaning                                 | who polls it       |
| -------------------- | --------------------------------------- | ------------------ |
| `/_oxide/health`     | socket bound, process alive             | K8s livenessProbe  |
| `/_oxide/ready`      | renderer warm — can serve page requests | LB, benchmarks     |

The pool init (~360ms `match;dur`) is paid **once at boot** instead of
**once per cold benchmark**, and benchmark scripts poll `/_oxide/ready`
so `start(ms)` / `ttfb(ms)` measure the server after it can actually
serve.

## Known gaps exposed by this run

1. **L0 server-side p50 is 1.07 ms (release), 7% over the §21 `< 1 ms`
   target.** The gap is small and distributed across the dispatch pipeline
   (rules eval, rate limiter, header assembly, CSP). Not a redesign; a
   targeted PERF pass to hoist the non-matching branch out of the hit path.
2. **`start(ms) = 1080-1369 ms`** — the trade for `ttfb = 140-189 ms`. A
   smaller worker pool warms faster, a larger one amortizes better; the
   current pool size is the balanced choice. Apps that can't afford a
   1.1s boot can set `oxide start --no-warmup` (a follow-up flag) and pay
   the pool init on the first request instead.
3. **`cold(ms)` variance is 30% between runs on the same host** — the
   gate's 5% threshold will trip on cold-build noise. Recommendation: pin
   the gate baseline from a **median of 3** consecutive quiet-host runs;
   a single run is not a baseline.
4. **HMR has one timeout in 15** — worth a look; not a regression from
   this session.

## What the gate covers

`benchmarks/gate.sh` compares a fresh `run.sh` table (cold build, warm
build, client bytes, server bytes, page count, start ms, RSS, TTFB)
against the committed copy of *this* report's first table and fails on a
>5% regression. The L0 latency table (`bench:cache`) and the HMR table
(`bench:hmr`) are not gated — their numbers are recorded here for
verification, and the CI jobs that run them are pass/fail on
correctness only, not regression. Gating the L0 and HMR tables by
threshold is a documented follow-up; the L0 hit-rate regression *is*
pinned (by `l0_hit_rate_999_of_1000_dispatches`).
